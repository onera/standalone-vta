# VTA baremetal FPGA software

This directory contains the C++ driver library, generated configuration files,
host-side scripts, and the ARM applications for running a quantized neural
network on the VTA accelerator in a Xilinx baremetal (no OS) environment.

## Directory layout

```
software/
├── apps/            # ARM application entry points, one main() each (the runners)
│   └── test_gemm/   # Standalone GEMM hardware correctness test
├── driver/          # Reusable C++ library, no main()
│   ├── include/     # Public headers; only these are included by apps/
│   └── src/         # Implementation; every .cc is compiled into every app
├── gen/             # Generated by the GenNnBaremetal codegen (make gen) - never hand-edit
│   └── sd_card/     # SD loader: the .bin set staged for copying to a FAT32 card
├── host/            # Host-side Python: runs on the development PC, not the board
│   └── nnbaremetal/ # The generator itself, one module per purpose
└── test/            # Host unit tests (no board, no model needed)
```

The runners are listed under [Deployment flows](#deployment-flows), the contents
of `gen/` under [Generate config files](#1---generate-config-files), the driver
headers under [C++ driver library](#c-driver-library), and the `host/` scripts
under [Host tooling](#host-tooling).

## Prerequisites

**Hardware / toolchain**

- Xilinx Vitis 2023.x - 2025.x (source `settings64.sh` before running Vitis scripts)
- A Vivado-exported XSA file for the target board
- For the `sd` data loader: a microSD card formatted **FAT32**, and a board whose
  SD controller MIO/clocks are configured by `ps7_init` / `psu_init`. The
  `xilffs` (FatFs) BSP library is enabled automatically by
  `create_vitis_workspace.py` (see [SD-card loader](#sd-card-loader))

**Python (host scripts)**

The host scripts need `pyserial` and `numpy`. Both come from the repo-wide
**pixi** environment defined in `pixi.toml` at the `standalone-vta` root; `pixi`
finds that manifest from any subdirectory, so prefix commands with `pixi run`:

```sh
cd modules/fpga/software
pixi run python host/uart_nn.py ...
pixi run make gen CONFIG=../../../config/vta_config.json
```

Every `python …` / `make …` command below assumes that environment. Use
`pixi shell` once instead if you prefer an activated shell.

## Deployment flows

Two axes are independent and can be combined freely:

| Axis            | Options                                              | Meaning                                              |
| --------------- | ---------------------------------------------------- | ---------------------------------------------------- |
| **Runner**      | `run_nn`, `run_nn_uart`, `run_nn_debug`, `run_nn_cpu_debug`, `test_gemm`, `sd_loader_test` | Which ARM application is compiled |
| **Data loader** | `tcl`, `elf`, `sd`                                   | How static model data (INSN/UOP/WGT/ACC) reaches DDR |

**Runner**

| Runner             | Input source                          | Behaviour                                                  |
| ------------------ | ------------------------------------- | ---------------------------------------------------------- |
| `run_nn`           | Pre-loaded in DDR (TCL / ELF / SD)    | Runs inference once and exits                              |
| `run_nn_uart`      | Received over UART each iteration     | Interactive loop driven by host                            |
| `run_nn_debug`     | fsim golden inputs (ELF or SD)        | Per-layer VTA isolation check vs fsim golden outputs       |
| `run_nn_cpu_debug` | fsim golden inputs (ELF or SD)        | Per-CPU-op isolation check vs the consumer layer's golden input |
| `test_gemm`        | Pre-loaded in DDR                     | Standalone GEMM correctness test (no data loader)          |
| `sd_loader_test`   | `test.bin` on the SD card             | Standalone SD read + read-back test (no data loader, no VTA driver) |

`run_nn_debug` (`NN_CHECK_LAYERS`) and `run_nn_cpu_debug`
(`NN_CHECK_CPU_OPS_ISO`) are debug builds. Both need golden data in DDR, so
they require the `elf` or `sd` loader plus the `--emit-layer-check` artifacts;
`tcl` will not load the references. See
[Per-layer isolation check](#4c---per-layer-isolation-check-run_nn_debug) and
[Per-CPU-op isolation check](#4d---per-cpu-op-isolation-check-run_nn_cpu_debug).

`test_gemm` and `sd_loader_test` are standalone: they take no `--data-loader`.

**Data loader**

| Loader | Static model data                            | input_nn.bin                                         |
| ------ | -------------------------------------------- | ---------------------------------------------------- |
| `tcl`  | `load_nn_static.tcl` sourced in XSDB         | `load_input.tcl` (run_nn) or UART (run_nn_uart)      |
| `elf`  | Embedded via `.incbin`; FSBL loads it        | `load_input.tcl` (run_nn) or UART (run_nn_uart)      |
| `sd`   | Read from a FAT32 SD card at boot by the app | From the card (run_nn) or UART (run_nn_uart)         |

Only `sd` frees the board from the host: `tcl` ties data loading to a live XSDB
session, and `elf` bakes the model into the image (a new model means a re-link).
With `sd` the board reads the `.bin` set itself at boot, so swapping the model
or the input is a card change. See [SD-card loader](#sd-card-loader).

## Full workflow

### 1 - Generate config files

After running the VTA compiler, pass its output directory to the baremetal
codegen. All files are written to `--outdir` (default: `gen/`) with fixed names.

The codegen is the Scala `fpga.host.GenNnBaremetal` task, run through Mill from
the repo root (the former Python `host/gen_nn_baremetal.py` + `host/nnbaremetal/`
package has been removed; the Scala port under
`modules/fpga/src/main/scala/host/` is the single implementation, shared with the
Mill example pipeline).

The `Makefile` wraps the common invocations, and is the easiest way in:

| Target          | What it generates                                                             |
| --------------- | ----------------------------------------------------------------------------- |
| `gen` / `gen-nn`| `gen/` from compiler output (headers + Tcl + `.incbin` artifacts)             |
| `gen-sd`        | `gen-nn` + `nn_sd_manifest.h` and the staged `gen/sd_card/` file set          |
| `gen-sd-debug`  | `gen-sd` + the isolation-check goldens on the card (needs `REF_DIR`)         |
| `gen-test_gemm` | `gen/init_dram.h` for `test_gemm` (no compiler output needed)                 |
| `test-cpu-ops`  | Builds and runs the host CPU-op unit test (no board, no model)                |
| `workspace`     | Vitis workspace (`XSA`, `CPU`, `RUNNER`, `DATA_LOADER`)                       |

```sh
make gen    CONFIG=../../../config/vta_config.json DDR_BASE=0x200000
make gen-sd CONFIG=../../../config/vta_config.json DDR_BASE=0x200000 SD_DIR=qyolo
```

Variables: `COMPILER_OUTPUT` (default `../../../compiler_output`), `CONFIG`,
`DDR_BASE` (`0x0`), `OUTDIR` (`gen`), `SD_DIR` (card root), `REF_DIR`
(`../../../simulators_output`), `RUNNER`, `DATA_LOADER`, `XSA`, `CPU`.

Calling the Mill task directly gives the full flag set (run from the repo root;
the active hardware config is selected by its file name via `-Dvta.config.file`):

```sh
./mill -Dvta.config.file=vta_config.json vta.fpga.software.genNnBaremetal <compiler_output_dir> \
    --ddr-base    0x200000      \
    --max-addr    0x1ff00000    \
    --outdir      gen           \
```

| Flag                  | Default | Description                                                                                                     |
| --------------------- | ------- | --------------------------------------------------------------------------------------------------------------- |
| `--outdir DIR`        | `gen`   | Directory for all generated files                                                                               |
| `--ddr-base ADDR`     | `0x0`   | Physical DDR base; all buffer offsets are relative to this                                                      |
| `--max-addr ADDR`     | -       | Upper DDR limit; script exits with error if any allocation exceeds it. Omitted = the fit check is skipped (warned) |
| `-Dvta.config.file=X` | `vta_config.json` | JVM prop (before the task name): VTA hardware config, read from `config/<X>` (block size + data widths). Replaces the old `--config-json` / `--block-size` flags |
| `--emit-sd-manifest`  | off     | Emit `nn_sd_manifest.h` and stage the `.bin` set into `<outdir>/sd_card/` for the `sd` data loader              |
| `--sd-dir NAME`       | root    | Subfolder on the card to read from (e.g. `qyolo_pattern`), so several models can share one card                 |
| `--emit-layer-check`  | off     | Emit per-layer isolation-check artifacts (`nn_debug_map.h` + golden in/out) for `run_nn_debug`. Requires `--ref-dir`. Off by default; normal images are unaffected. |
| `--emit-cpu-check`    | off     | Emit `nn_cpu_debug_map.h` for `run_nn_cpu_debug`; reuses the same golden regions and implies `--emit-layer-check` |
| `--ref-dir DIR`       | -       | Directory with fsim golden dumps (`--dump-layers`): `input<SUFFIX>.bin` / `output<SUFFIX>.bin`. Required with `--emit-layer-check`. |
| `--verbose`           | off     | Print the DRAM layout summary                                                                                   |

The script warns on non-default configurations:

- **8-bit data width** (`LOG_INP_WIDTH` or `LOG_OUT_WIDTH` = 3): CPU ops use `int8_t`;
  ensure compiler output and network quantization match.
- **Asymmetric stride** (`sh ≠ sw`): the functional simulator's `im2row` only supports
  isotropic stride; simulation results will differ from FPGA execution.

**Generated files**

| File                 | Description                                                                                                                               |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `vta_hw_config.h`    | C++ type aliases (`vta_inp_t`, `vta_out_t`, `vta_acc_t`, `VTA_BLOCK_SIZE`) derived from the hardware config; required by `vta_cpu_ops.cc` |
| `nn_ddr_map.h`       | `LayerDesc nn_layers[]` - VCR register values and buffer addresses per VTA layer                                                          |
| `nn_exec_plan.h`     | `NnExecStep nn_exec_steps[]` - ordered VTA + CPU steps for the full model                                                                 |
| `nn_debug_map.h`     | _(only with `--emit-layer-check`)_ `DebugLayerDesc nn_debug[]` - per-layer golden input/output addresses + input destination buffer       |
| `nn_cpu_debug_map.h` | _(only with `--emit-cpu-check`)_ `DebugCpuStep nn_cpu_debug[]` - per-CPU-op golden source/expected addresses                              |
| `load_nn_static.tcl` | XSDB: loads INSN/UOP/WGT/ACC only (no input)                                                                                              |
| `load_nn.tcl`        | XSDB: loads INSN/UOP/WGT/ACC + input_nn.bin                                                                                               |
| `load_input.tcl`     | XSDB: loads input_nn.bin only (companion for ELF loader or standalone)                                                                    |
| `nn_bin_data.S`      | AArch64 assembly with `.incbin` for each static buffer                                                                                    |
| `nn_vta_sections.ld` | Linker fragment placing each `.vta_lN_*` section at its DDR address                                                                       |
| `nn_sd_manifest.h`   | _(only with `--emit-sd-manifest`)_ `vta::SdFile nn_sd_static_files[]` + `nn_sd_input_file` - filename → DDR address map read at boot      |
| `sd_card/`           | _(only with `--emit-sd-manifest`)_ the `.bin` files themselves, staged for copying to the card                                            |

### 2 - Create the Vitis workspace

The script creates a platform from an XSA, builds the BSP, and creates an
application component with VTA driver linked in.
`--runner` and `--data-loader` allows to specify which applications to create.

**Create workspace and application for the first time:**

```sh
source /opt/Xilinx/2025.2/Vitis/settings64.sh

vitis -s host/create_vitis_workspace.py \
    --xsa         path/to/design.xsa  \
    --workspace   path/to/vitis_workspace    \
    --runner      run_nn_uart         \
    --data-loader tcl
```

**Add a new application to an existing workspace** (platform already built,
`--xsa` omitted):

```sh
vitis -s host/create_vitis_workspace.py \
    --workspace   path/to/vitis_workspace    \
    --runner      run_nn_uart         \
    --data-loader tcl                 \
    --app-name    my_app
```

**Create multiple app components in one call:**

```sh
vitis -s host/create_vitis_workspace.py \
    --xsa         path/to/design.xsa  \
    --workspace   build/vitis_proj    \
    --runner      run_nn run_nn_uart  \
    --data-loader elf tcl
```

| Flag                        | Default                               | Description                                                                               |
| --------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------- |
| `--xsa PATH`                | _(required for first run)_            | Vivado XSA file; omit to reuse an existing platform                                       |
| `--workspace PATH`          | `vitis_workspace`                     | Vitis workspace directory                                                                 |
| `--platform-name NAME`      | `vta_platform`                        | Name of the hardware platform component                                                   |
| `--runner`                  | `run_nn`                              | One or more of `run_nn`, `run_nn_uart`, `run_nn_debug`, `run_nn_cpu_debug`, `test_gemm`, `sd_loader_test`; creates one app component per runner |
| `--data-loader tcl\|elf\|sd`| _(required for the run_nn\* runners)_ | Selects which generated config files are copied into the app, and sets `NN_SD_LOADER` for `sd`; not used for `test_gemm` / `sd_loader_test`. The debug runners need `elf` or `sd`. |
| `--cpu NAME`                | `psu_cortexa53_0`                     | BSP processor instance name; check `xparameters.h` in your BSP for the correct value      |
| `--app-name NAME`           | `vta_<runner>_<loader>`               | Override the app component name (single runner only)                                      |
| `--baud N`                  | `115200`                              | UART baud rate compiled into the firmware (`VTA_UART_BAUD`)                               |
| `--pl-reset-between-layers` | off                                   | `run_nn_debug` only: pulse a PL-only fabric reset (ZynqMP `pl_resetn0`, GPIO pin 173) before each layer, so every layer runs on pristine VTA state. Adds `NN_PL_RESET_BETWEEN_LAYERS`. |
| `--dry-run`                 | -                                     | Print files that would be copied without calling Vitis APIs                               |

App component names are auto-derived: `vta_run_nn_tcl`, `vta_run_nn_uart_elf`,
`vta_run_nn_sd`, `vta_test_gemm`, etc.

The script also patches Vitis generated files:

- for the `elf` data loader, it adds inside the application linker script:

```
INCLUDE nn_vta_sections.ld
```

- it includes the driver sources in the user cmake file as well as the \*.S assembly files required by the `elf`` flow

For the `sd` data loader (or the `sd_loader_test` runner), it also enables the
**xilffs** (FatFs) BSP library on the platform domain, with long filenames
(`XILFFS_use_lfn=1`) - the loader opens compiler basenames like
`instructions_L0.bin`, which exceed FAT 8.3. This happens **before**
`platform.build()`, so it only takes effect when the platform is created: to add
an `sd` app to a workspace whose platform was already built without xilffs, use
a fresh `--workspace` directory (or enable xilffs by hand in the BSP settings).

### 3 - Build and deploy

Build the application in Vitis, then load the ELF and static model data:

```sh
# In the Vitis XSDB console (or xsct shell):
connect
targets -set -filter {name =~ "psu_cortexa53_0"}
dow path/to/application.elf

# TCL data loader - load static model data:
source gen/load_nn_static.tcl

# run_nn only - also load the input:
source gen/load_input.tcl
```

For the `elf` data loader, static model data is already embedded in the ELF.
Only source `load_input.tcl` when using `run_nn` (not needed for `run_nn_uart`).

For the `sd` data loader, nothing is pushed over JTAG: the app reads the model
(and, for `run_nn`, the input) from the card itself. The PS still has to have
run `ps7_init` / `psu_init` so the SD MIO pins and clocks are configured, which
a boot from the card does for you, and XSDB's `loadhw` / the FSBL does in a
JTAG session. See [SD-card loader](#sd-card-loader).

### 4a - One-shot inference (`run_nn`)

The ARM application runs the full inference pipeline once and exits, printing
per-step logs. Input must be pre-loaded before execution starts (via TCL, or
ELF + `load_input.tcl`, or read from the SD card).

```
=== VTA NN runner: <N> step(s) ===
[vta] step 0/<N-1>: <name>
...
=== NN done ===
```

### 4b - UART interactive loop (`run_nn_uart`)

The ARM application boots, prints the input/output sizes, then loops: waits
for a trigger byte, receives input over UART, runs inference, and sends back
the output. Only static model data needs to be pre-loaded; `uart_nn.py`
handles the input/output exchange.

**Protocol**

```
Board → "=== VTA NN runner: <N> step(s) ===\r\n"   (once, at boot)
Loop:
  Host  → 0x01  (trigger byte)
  Board → "input=<N> out=<M>\r\n"
  Board → "READY\r\n"
  Host  → <input_n_bytes> raw HWC INT8 bytes
  Board   (runs inference, prints per-step logs)
  Board → "OUTPUT\r\n"
  Board → <out_n_bytes> raw bytes
```

**`uart_nn.py` - host client**

```sh
# Single run:
python host/uart_nn.py \
    --port /dev/ttyUSB0 \
    --input  input_nn.bin \
    --output out.bin

# Multiple inputs → results/:
python host/uart_nn.py \
    --port /dev/ttyUSB0 \
    --input img1.bin img2.bin \
    --output-dir results/

# Show per-layer step and cycle logs:
python host/uart_nn.py \
    --port /dev/ttyUSB0 \
    --input input_nn.bin --output out.bin \
    --verbose
```

| Flag                   | Default         | Description                                                       |
| ---------------------- | --------------- | ----------------------------------------------------------------- |
| `--port DEV`           | _(required)_    | Serial device (`/dev/ttyUSB0`, `COM3`, …)                         |
| `--baud N`             | `115200`        | Baud rate (must match `VTA_UART_BAUD` compiled into the firmware) |
| `--input FILE …`       | _(required)_    | Raw input file(s); one inference per file                         |
| `--output FILE`        | -               | Output file (single-run shorthand)                                |
| `--output-dir DIR`     | -               | Directory for per-run output files                                |
| `--repeat N`           | `1`             | Repeat each input N times                                         |
| `--input-bytes N`      | _(from banner)_ | Override input size (banner still consumed)                       |
| `--output-bytes N`     | _(from banner)_ | Override output size (banner still consumed)                      |
| `--banner-timeout SEC` | `40`            | Seconds to wait for banner after sending trigger                  |
| `--ready-timeout SEC`  | `60`            | Seconds to wait for `READY` before each run                       |
| `--verbose`            | -               | Print per-layer board logs during inference                       |
| `--detile`             | -               | Convert VTA block output to NCHW flat before saving               |
| `--output-shape C,H,W` | -               | Required with `--detile`; output tensor shape                     |
| `--block-size N`       | `16`            | VTA block size used for de-tiling                                 |
| `--check [FILE]`       | -               | Compare the received output against a reference; the bare flag defaults to `simulators_output/final_output.bin` |

### 4c - Per-layer isolation check (`run_nn_debug`)

A debug build that pinpoints which VTA layer first produces wrong data on the
board. Instead of chaining layers (where one corrupt output cascades into all
later layers), it runs **each VTA layer in isolation on fsim-precomputed golden
inputs** and compares its raw output (pre-rescale) against the fsim golden
output. The first layer reporting a mismatch is the true source of corruption.

It reuses the unmodified `run_layer()`; `run_nn` / `run_layer` / `LayerDesc`
are untouched. The whole path is gated by the `NN_CHECK_LAYERS` compile
definition (set automatically for the `run_nn_debug` runner), so normal images
carry no reference data.

**1. Generate the golden dumps with the functional simulator:**

```sh
# from the functional_simulator dir; RUNTIME_FLAGS is forwarded to ./build/fsim
make fsim RUNTIME_FLAGS=--dump-layers
# -> input<SUFFIX>.bin and output<SUFFIX>.bin per VTA layer, in the output dir
```

`examples/`'s `fsim_inference` target does not forward runtime flags, so it
cannot produce the dumps - use `make fsim` above, or call the binary directly
with `./build/fsim --dump-layers`.

**2. Generate the board artifacts with the golden data embedded:**

```sh
./mill -Dvta.config.file=vta_config.json vta.fpga.software.genNnBaremetal <compiler_output_dir> \
    --ddr-base    0x10000000                          \
    --emit-layer-check                                \
    --ref-dir     <repo>/simulators_output
```

The golden inputs/outputs are placed in a reserved DRAM region above all live
allocations, embedded as extra `.vta_lN_inref` / `.vta_lN_outref` `.incbin`
sections in `nn_bin_data.S`, placed by `nn_vta_sections.ld`, and described by
`nn_debug_map.h`. Layers whose dumps are missing are skipped (zero sizes).

**3. Create the app (`NN_CHECK_LAYERS` set automatically):**

```sh
vitis -s host/create_vitis_workspace.py \
    --workspace   path/to/vitis_workspace \
    --runner      run_nn_debug            \
    --data-loader elf
```

Use `--data-loader sd` instead to read the model and the goldens from the card
(generate them with `make gen-sd-debug`, or `--emit-sd-manifest
--emit-layer-check --ref-dir …`). Add `--pl-reset-between-layers` to pulse a
PL-only fabric reset before each layer, so a layer cannot inherit VTA state left
by the previous one.

**4. Build, `dow application.elf`, `con`, and read the UART.** Each layer prints
either `PASS` or `FAIL k/N mismatches` (with the first differing elements). The
earliest `FAIL` is the VTA-introduced corruption - fed golden inputs, so it is
not a cascade artifact.

> Note: this cannot be reproduced in simulation - fsim and the Verilated RTL
> match the golden references by construction. It is an on-board diagnostic.

### 4d - Per-CPU-op isolation check (`run_nn_cpu_debug`)

The host-side sibling of `run_nn_debug`: it isolates the **CPU** ops rather than
the VTA layers. Each `FORMAT_INPUT` / `IM2ROW` / `INT32_CHAIN` step runs alone on
a known-good upstream golden, and its output buffer is compared against the
downstream VTA layer's golden input dump (`input<SUFFIX>.bin`) - equal by
construction, since that CPU op is what writes that buffer. Between the two
runners, a divergence can be attributed to either the accelerator or the PS code.

No new fsim dumps are needed: it reuses the goldens `--emit-layer-check` already
places. Gated by `NN_CHECK_CPU_OPS_ISO`, set automatically for the runner.

```sh
# 1. Same golden dumps as 4c, plus the CPU-op map (--emit-cpu-check implies
#    --emit-layer-check):
make gen-sd-debug CONFIG=../../../config/vta_config.json DDR_BASE=0x10000000

# 2. Create the app (elf works too; tcl will not load the references):
vitis -s host/create_vitis_workspace.py \
    --workspace   path/to/vitis_workspace \
    --runner      run_nn_cpu_debug        \
    --data-loader sd
```

Build, `dow application.elf`, `con`, and read the UART: each step prints `PASS`
or `k/N mismatches`. The first mismatching step is the CPU-op-introduced
corruption.

## SD-card loader

The `tcl` and `elf` loaders both tie the board to the host: `tcl` needs a live
XSDB session pushing every `.bin` over JTAG, and `elf` bakes the model into the
image, so a new model means a re-link. The `sd` loader removes both: the app
reads the `.bin` set from a FAT32 card into DDR itself at boot, so a deployed
board runs standalone and swapping the model or the input is a card change.

**How it works.** `--emit-sd-manifest` writes `gen/nn_sd_manifest.h`, a
filename → DDR address table compiled into the ELF, and stages the referenced
files into `gen/sd_card/`. At boot the app calls `vta::sd_load_files()`
(`driver/src/vta_sd.cc`), which mounts the card, reads each entry to its address
in 64 KiB chunks, checks the size against the manifest, and flushes the written
range from cache so the VTA's AXI reads see the bytes. Any error is printed over
UART and aborts the run.

The manifest holds three groups, so the same generated header serves every
runner:

| Array                   | Contents                                       | Read by                                   |
| ----------------------- | ---------------------------------------------- | ----------------------------------------- |
| `nn_sd_static_files[]`  | INSN / UOP / WGT / ACC + CPU-op param blobs    | every runner                              |
| `nn_sd_input_file`      | `input_nn.bin` (if present)                    | every runner except `run_nn_uart`, which takes its input over UART |
| `nn_sd_ref_files[]`     | fsim goldens (`--emit-layer-check`)            | `run_nn_debug`, `run_nn_cpu_debug`        |

Addresses come from the same layout code as the Tcl and `.incbin` emitters, so
all three loaders place identical bytes at identical addresses. Runtime ACC
buffers (dynamic input, not static bias) are excluded, exactly as elsewhere.

### Flow

```sh
# 1. Generate the manifest + staged file set (SD_DIR is optional).
make gen-sd CONFIG=../../../config/vta_config.json DDR_BASE=0x10000000 SD_DIR=qyolo

# 2. Copy the staged set to the root of a FAT32 card, preserving any subfolder.
cp -r gen/sd_card/* /path/to/mounted/card/

# 3. Create the app; xilffs is enabled on the platform automatically.
vitis -s host/create_vitis_workspace.py \
    --xsa         path/to/design.xsa    \
    --workspace   path/to/vitis_workspace \
    --runner      run_nn                \
    --data-loader sd
```

Then insert the card, build in Vitis, and run. In an XSDB session the PS must be
initialized first so the SD MIO pins and clocks exist:

```sh
fpga path/to/design.bit
targets -set -filter {name =~ "APU*"}; rst
loadhw path/to/design.xsa      # runs ps7_init / psu_init -> SD MIO + clocks
dow path/to/application.elf
con
```

The board prints one line per file, then runs:

```
sd_load: 0:/qyolo/instructions_L0.bin -> 0x10000000 (2048 bytes)
...
=== VTA NN runner: <N> step(s) ===
```

Booting from the card instead (FSBL from the same card) needs no JTAG at all:
`ps7_init` / `psu_init` runs as part of the boot, which is the point of this
loader.

### Multiple models on one card

`--sd-dir NAME` (`SD_DIR=NAME`) bakes a subfolder into the manifest as
`NN_SD_DIR`, so the app opens `0:/NAME/<file>` and several models can share a
card. It is also the staging subfolder, and regenerating clears only that
folder, leaving sibling models intact. Default is the card root. Because the
folder is compiled into the ELF, each model still needs its own build.

### Notes and constraints

- **FAT32 only**, and long filenames must be enabled in the BSP
  (`XILFFS_use_lfn=1`, done automatically): the loader opens compiler basenames
  like `instructions_L0.bin`, well past FAT 8.3.
- **xilffs is enabled at platform creation.** Adding an `sd` app to a workspace
  whose platform was built without it needs a fresh `--workspace`.
- `driver/src/vta_sd.cc` is guarded by `NN_SD_LOADER`: `UserConfig.cmake` globs
  every `driver/src/*.cc` into every app, but `ff.h` only exists on `sd` builds,
  so the whole unit preprocesses away for `tcl` / `elf`.
- Regenerate **and re-copy** the card after any change to the model, `CONFIG`,
  or `--ddr-base`. The manifest's addresses and sizes are checked at load time,
  so a stale card fails loudly rather than silently computing garbage.

### `sd_loader_test` - bring-up

Before wiring a board into the full flow, `sd_loader_test` proves the SD read
path on its own: it depends only on the BSP + xilffs (no VTA driver, no
generated headers, no data loader). It reads `0:/test.bin` into DDR, then
re-reads it window-by-window into a staging buffer and compares against DDR
after invalidating the range - which is what catches cache/DMA coherency bugs,
not just "did the file open".

```sh
# Any file works; copy it to the card root as test.bin, then (from the repo root):
./mill vta.fpga.software.sdChecksum test.bin        # expected size + checksum

vitis -s host/create_vitis_workspace.py \
    --xsa       path/to/design.xsa      \
    --workspace path/to/sd_test_ws      \
    --runner    sd_loader_test
```

Build, initialize the PS as above, `dow sd_loader_test.elf`, `con`. Expect the
byte count and checksum to match `mill vta.fpga.software.sdChecksum`, and a final `READBACK OK`.
`READBACK MISMATCH`, or an `f_mount` failure, means the SD path is broken and
the full loader will not work either. The app caps reads at 16 MiB and writes to
`0x10000000` (see the tunables at the top of `apps/sd_loader_test.cc`).

## C++ driver library

The library has no dependencies beyond the Xilinx BSP (included by Vitis).

| Header          | Contents                                                                                                                                                          |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vta.h`         | VCR register layout, `CTRL_LAUNCH` / `CTRL_DONE` bit definitions                                                                                                  |
| `vta_board.h`   | `board_init(baud)` - reinitializes the PS UART to the given baud rate at startup                                                                                  |
| `vta_ctrl.h`    | `launch()`, `poll_done()` - thin wrappers around VCR MMIO                                                                                                         |
| `vta_mem.h`     | `init_ddr_region()`, `dump_words()` - DDR init and debug helpers                                                                                                  |
| `vta_nn.h`      | `LayerDesc`, `run_layer()`, `run_nn()`, `find_input()`                                                                                                            |
| `vta_nn_debug.h`| `DebugLayerDesc`, `check_layer_output()`, `run_nn_debug()` - per-layer isolation checker; active only when built with `NN_CHECK_LAYERS` (no-op otherwise)         |
| `vta_cpu_ops.h` | `NnStepType`, `NnExecStep`, and the step structs `NnFormatInputStep`, `NnIm2RowStep`, `NnQaddStep`, `NnConcatStep`, `NnDequantStep`, `NnQuantStep`, `NnRescaleStep`, `NnInt32ChainStep`, `NnConvTransposeStep`, plus the corresponding `vta::run_*()` functions |
| `vta_cpu_ops_debug.h` | `DebugCpuStep`, `run_nn_cpu_debug()` - per-CPU-op isolation checker; active only when built with `NN_CHECK_CPU_OPS_ISO` (no-op otherwise)                   |
| `vta_sd.h`      | `SdFile`, `sd_load_files()` - reads the manifest's files from a FAT32 card into DDR and flushes them. Needs the `xilffs` BSP library; compiled only when `NN_SD_LOADER` is set |
| `vta_pl_reset.h`| `pl_reset()` - pulses the PL-only fabric reset (ZynqMP `pl_resetn0`, PS GPIO pin 173). Leaves the PS, DDR, and caches untouched; only call when the PL is idle |

`board_init()` must be called at the very top of `main()`, before any
`xil_printf` / `inbyte` / `outbyte`. On Zynq-7000 / Zynq UltraScale+ the BSP's
pre-compiled `libxil.a` boots the UART at 115200 and `board_init()`
reinitializes it to `VTA_UART_BAUD` at runtime, so no BSP rebuild is required.

On Versal (vck190, vek280) it is a **no-op**: those parts drive the PS UART
through the PL011-based `XUartPsv` driver and their BSP ships no `xuartps.h`,
so `vta_board.cc` gates the whole body on `XPAR_XUARTPS_0_BASEADDR &&
!versal && !VERSAL_NET`. There the BSP-configured baud rate stands, and the
`--baud` passed to `create_vitis_workspace.py` must match it.

`run_nn.cc`, `run_nn_uart.cc`, `run_nn_debug.cc` and `run_nn_cpu_debug.cc` all
call it as their first statement.

`run_layer()` handles the full hardware interaction for one layer: flush input
caches, program VCR registers, launch VTA, poll for completion, and invalidate
the output cache.

## Host tooling

`host/` holds the two host scripts with no Scala equivalent: `create_vitis_workspace.py`
(drives the Vitis Python API) and `uart_nn.py` (serial board I/O). Both run in the
pixi environment (`pixi run python host/<script>.py`).

The former standalone Python helpers have been ported to Scala and are now run
through Mill from the repo root (they share the same code the codegen and the
example pipeline use):

| Mill task                         | Purpose                                                                                                   |
| --------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `vta.fpga.software.checkOutput <dump>`     | Detiles a board output dump to NCHW and diffs it against the fsim `simulators_output/final_output.bin`      |
| `vta.fpga.software.auditDram <comp-dir>`   | Runs the generator's layout guards (overlap / fit / `--max-addr`) on a compiler output dir and prints the DRAM map, without emitting anything. Useful to sanity-check a non-zero `--ddr-base` relocation, since fsim and the compiler both use `0x0` |
| `vta.fpga.software.sdChecksum <file>`      | Size + 32-bit additive checksum of a file, matching what `sd_loader_test` prints over UART                |
| `vta.fpga.software.genInitDramTestGemm`    | Generates `gen/init_dram.h` for `test_gemm` (`make gen-test_gemm`); needs no compiler output              |

`make test-cpu-ops` builds and runs `test/test_cpu_ops.cc` on the host: it
compiles the real `driver/src/vta_cpu_ops.cc` against stubs in `test/host/` and
checks it against the functional simulator's header-only reference on synthetic
inputs. No board, no model, and no fsim run needed - just a host `g++`, which
makes it the fastest way to catch a CPU-op regression.
